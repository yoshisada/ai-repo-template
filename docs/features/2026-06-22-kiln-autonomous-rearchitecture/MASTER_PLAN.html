§1Executive Summary

Kiln ships today as a skill-invoked, human-paced build pipeline. This plan upgrades it to a context-informed autonomous loop: every build reads its own accumulated precedent, follows per-project coding standards, and self-advances based on declared review preferences.

The loop closes because mistakes flow into Obsidian, Obsidian is searchable before each build, and self-improvement proposals auto-classify into either applied L1 patches or human-reviewed chips. Three invariants are preserved throughout:

  • Propose-don't-apply — kiln never auto-merges its own skill edits; only config edits (L1) may be auto-applied
  • Hooks are the floor — 4-gate enforcement stays; new coverage + traceability hooks are additive
  • Wheel stays plugin-agnostic — all kiln workflow JSONs live in plugin-kiln/workflows/

§1.5Design Philosophy — Agent-First, Rightsized Model

Core principle: Every workflow step that involves reasoning, judgment, or synthesis MUST be an agent step. Command steps are reserved for pure mechanical operations: file reads, git commands, JSON slicing, process management. When in doubt, make it an agent.

The corollary: the model tier must match the task. Running sonnet on a classification task haiku can handle wastes latency and cost. Running haiku on complex design produces shallow output.

Journal as Orchestrator State Source of Truth

The run journal (.kiln/runs/<id>/journal.md) is the canonical state for the orchestrator session — not conversation history. After each step completes, one structured line is appended: 
[step: specify] [verdict: pass] [output: specs/auth/spec.md] [cost: $0.03]

Why this matters for session management: Claude Code's auto-compact can summarize and compress conversation history at any time. This is safe because the orchestrator session is intentionally thin — it dispatches wheel steps and reads step outputs from disk. All decision-relevant state (verdicts, output paths, costs, errors) lives in the journal and .wheel/outputs/, not in session context. On --resume, the orchestrator reads the journal to reconstruct exactly where the run is, making compact irrelevant to correctness.

Implication: the orchestrator must never make a decision based on "what the previous agent said in the conversation." It reads .wheel/outputs/<step>-verdict.json. The conversation is a display surface, not a state store.

Checkpoint Pause Logic

Checkpoints are command steps — no AI reasoning. A checkpoint pauses on exactly two conditions:

  1. Config-determined (roadmap): the checkpoint name is in review_checkpoints[] in .kiln/config.json. Set during kiln-init and reflects the project's pre-declared review cadence.
  2. Critical-event override: an upstream step wrote severity: blocking in its verdict JSON. A blocking finding always pauses regardless of config.
Example: checkpoint-pre-pr checks review_checkpoints[] and audit-verdict.severity. If neither triggers, it skips automatically. No model call, no reasoning — just two jq lookups and a branch. The human's declared cadence governs; the system doesn't second-guess it mid-run.

Failure Recovery — Debugger Loop + Notification

When a workflow step fails, the system does not retry blindly. The recovery sequence is:

AGT

Command steps with transient failure modes (gh CLI, network calls) get "retry": 2 before the debugger is invoked. Agent/team steps go straight to the debugger — retrying the same prompt produces the same failure. build-summary and the post hook always run ("on": "always") regardless of pipeline status.

External MCP Graceful Degradation

Any workflow step that depends on an external MCP (Obsidian, Notion, etc.) MUST have "on_failure": "skip". External MCPs can be unavailable at any time and a build should never block on them.

The skip pattern: the command falls back to writing an empty stub output with a warning message, so downstream steps that context_from it receive something rather than nothing. The warning surfaces in the build summary Findings as info severity.

kiln-next — Human Orientation Command

kiln-next is human-only — never auto-invoked by any pipeline or workflow. It runs at session start to tell the human what needs their attention. It evaluates a fixed priority stack and short-circuits at the first match.

Two-track model: issues are always fix-priority — the track is determined by count vs issue_batch_threshold. Small batch → kiln-fix per issue (targeted, no spec overhead). Large batch → kiln-build-prd (enough work to warrant full spec → plan → implement). Feedback + roadmap items are strategic, not urgent — they accumulate and kiln-distill bundles them into feature PRDs. These two tracks never mix: issues don't get distilled, feedback doesn't get fixed.

kiln-init Onboarding Flow

kiln-init is idempotent. It checks whether .kiln/config.json already exists and reads its config_version field:

  • First run (no config): runs the full 6-step wizard.
  • Re-run (config exists): compares config_version against the current package's config-schema.json, identifies keys introduced since the project's version, and asks only about those. If nothing is new, prints "config is up to date" and exits.

No separate update subcommand — kiln-init is the single entry point for both cases. Version detection uses a config-schema.json shipped with the plugin that maps each key to the version that introduced it.

// plugin-kiln/scaffold/config-schema.json
{
  "1.0.0": ["review_mode", "review_checkpoints", "notifications", "models", "standards", "auto_build", "branching"],
  "1.1.0": ["pi_apply_threshold"]
}
// .kiln/config.json carries: "config_version": "1.0.0"

On re-run, kiln-init asks only about keys in versions > config_version, then bumps config_version on save. Existing answers are never overwritten.

When auto_build: true is set in config.json, kiln-distill automatically enqueues kiln-build-prd after the PRD is written — completing the loop without a manual hand-off step.

.kiln/standards.md — Coding Standards Template

A Clean Code–shaped template injected at the planner and implementer stages. Swappable: the standards key in config.json can point to any file (e.g. a SOLID-focused alternative).

Inject points: compose-context.sh --standards reads this file and prepends it as a ## Coding Standards block in the prompt prefix for both the plan agent and the implement team. Standards set during planning propagate forward because bad names in contracts/interfaces.md contaminate the entire implementation. 
## Coding Standards

### Naming
- names are pronounceable and searchable — no abbreviations, no encodings
- one word per concept (fetch not retrieve/get/pull mixed across codebase)
- functions named as verbs, booleans as predicates (isActive, hasPermission)

### Functions
- do one thing at one level of abstraction
- ≤ 20 lines, ≤ 2 parameters — extract an object or split if more are needed
- no flag arguments — split into two named functions instead
- no side effects — a function that says it reads should only read

### Comments
- do not comment WHAT the code does — rename or restructure instead
- only write a comment to explain WHY: a hidden constraint, a non-obvious invariant

### Error handling
- throw exceptions, never return null or error codes from internal functions
- never pass null — guard at system boundaries, trust contracts internally

### Structure
- single responsibility — one reason to change per module
- tell don't ask — don't reach into an object's state to make decisions for it
- no circular dependencies across layers

### Tests
- one concept per test, assertion names describe the failure
- every test references its spec FR in a comment

Key Design Decisions

  • Standards injected at plan time — not just at implement. Bad names in contracts/interfaces.md propagate everywhere; catching them at plan time prevents downstream drift.
  • Precedent injected at specify + plan + implement — same precedent block read by all three agents so warnings can't be forgotten in a later stage.
  • Structured JSON verdicts — each agent step emits {agent, verdict:pass|fail|warn, ...} so downstream steps can gate on the result without prose parsing.
  • Checkpoints are command scripts, not agents — pause decisions are pre-configured (review_checkpoints[] set during kiln-init) or triggered by a critical upstream event (severity: blocking from an audit/implement verdict). No AI reasoning mid-run. If neither condition applies, the checkpoint skips automatically.
  • Resumable via cursor — .kiln/runs/<id>/manifest.json stores the last completed step; wheel-run can resume from any step. All three major workflows support --resume: kiln-build-prd (interrupted mid-pipeline), kiln-fix (interrupted mid-debug), kiln-distill (interrupted mid-draft). kiln-next surfaces the resume command when it detects an interrupted run manifest.

§12.5Workflow Pre/Post Hooks

Every wheel workflow JSON may declare a hooks block with pre and post command steps. These run outside the step graph — before any steps start (pre) and after the last step completes (post). Command-only; no agent steps in hooks.

Use case: push an observability snapshot, fire a Slack notification, append to a build log, or send metrics to any endpoint — without touching the domain steps.

Schema

{
  "name": "kiln-build-prd",
  "version": "1.0.0",
  "hooks": {
    "pre": {
      "command": "curl -s -X POST \"$WEBHOOK_URL\" -d '{\"event\":\"workflow.start\",\"run_id\":\"$WHEEL_RUN_ID\"}' || true",
      "env_required": ["WEBHOOK_URL"]
    },
    "post": {
      "command": "bash \"${WORKFLOW_PLUGIN_DIR}/scripts/push-obs-snapshot.sh\" \"$WHEEL_RUN_ID\" \"$WHEEL_STATUS\"",
      "on": "always",
      "env_required": ["OBS_ENDPOINT"]
    }
  },
  "steps": [...]
}

Fields

FieldRequiredDefaultDescription
hooks.pre.commandyes (if pre block exists)—Shell command run before step 1
hooks.post.commandyes (if post block exists)—Shell command run after last step
hooks.post.onnoalwaysalways · success · failure
hooks.pre.env_requiredno[]If any listed var is unset, skip hook with a warning — no abort
hooks.post.env_requiredno[]Same — hook self-skips gracefully when destination not configured

Wheel-exported variables available in hook commands

VariableAvailable atValue
$WHEEL_RUN_IDpre + postUUID for this workflow run
$WHEEL_WORKFLOW_NAMEpre + poste.g. kiln-build-prd
$WHEEL_WORKFLOW_VERSIONpre + poste.g. 1.0.0
$WHEEL_STATUSpost onlypass · fail · warn
$WHEEL_STEP_COUNTpost onlyTotal steps that executed
$WHEEL_STEPS_PASSEDpost onlySteps that exited 0
$WHEEL_OUTPUTS_DIRpre + post.wheel/outputs/
$WORKFLOW_PLUGIN_DIRpre + postAbsolute path to plugin dir
Pre-hooks that fail (non-zero exit) emit a warning but do not abort the workflow. Post-hooks that fail are logged but do not change the workflow exit status. Use || true defensively when the destination may be unavailable.

Example hook commands

# Slack notification on completion
curl -s -X POST "$SLACK_WEBHOOK_URL" \
  -H 'Content-Type: application/json' \
  -d "{\"text\":\"*${WHEEL_WORKFLOW_NAME}* finished: ${WHEEL_STATUS} (${WHEEL_STEPS_PASSED}/${WHEEL_STEP_COUNT} steps)\"}" || true

# Lightweight HTTP observability endpoint
curl -s -X POST "http://localhost:9000/events" \
  -d "run_id=${WHEEL_RUN_ID}&workflow=${WHEEL_WORKFLOW_NAME}&status=${WHEEL_STATUS}" || true

# Append to a shared TSV build log
echo "$(date -u +%FT%TZ)\t${WHEEL_WORKFLOW_NAME}\t${WHEEL_RUN_ID}\t${WHEEL_STATUS}" \
  >> "${HOME}/.kiln/build-log.tsv"

# Push outputs snapshot to Obsidian via plugin script
bash "${WORKFLOW_PLUGIN_DIR}/scripts/push-obs-snapshot.sh" \
  "${WHEEL_RUN_ID}" "${WHEEL_STATUS}" "${WHEEL_OUTPUTS_DIR}" || true

Wheel runtime changes required

  • Parse hooks.pre and hooks.post from workflow JSON on load
  • Check env_required before running each hook; skip with WARN: hook skipped — $VAR unset if any var missing
  • Run pre-hook in a clean subshell with wheel context vars exported
  • Run post-hook after final step once WHEEL_STATUS is resolved
  • Both hooks share the same $WORKFLOW_PLUGIN_DIR templating used by agent steps
  • Add hooks block to workflow-format.md template reference

standards-template.md content

## Coding Standards

### Naming
- names are pronounceable and searchable — no abbreviations, no encodings
- one word per concept (fetch not retrieve/get/pull mixed across the codebase)
- functions named as verbs, booleans as predicates (isActive, hasPermission)
- classes/modules named as nouns describing what they ARE, not what they DO

### Functions
- do one thing at one level of abstraction
- <= 20 lines, <= 2 parameters — extract an object or split if more are needed
- no flag arguments — split into two named functions instead
- no side effects — a function that says it reads should only read

### Comments
- do not comment WHAT the code does — rename or restructure instead
- only write a comment to explain WHY: a hidden constraint, a non-obvious invariant

### Error handling
- throw exceptions, never return null or error codes from internal functions
- never pass null — guard at system boundaries, trust contracts internally

### Structure
- single responsibility — one reason to change per module
- tell don't ask — don't reach into an object's state to make decisions for it
- no circular dependencies across layers

### Tests
- one concept per test, assertion names describe the failure
- every test references its spec FR in a comment
- no stubs on integration paths
