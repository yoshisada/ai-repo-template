Re-architecting the Kiln Build Cycle

An autonomous, self-improving, observable, and forkable build loop — built from a critical audit of what exists today.

Goal: a skill flips a flag and Claude builds a project mostly autonomously from a plan + design — while the system watches its own pitfalls and improves during the build, you watch it happen, and anyone who forks it gets a loop that self-improves on their precedent.

How to read this: §1 diagnosis (with evidence). §2 the input (vision as apex). §3 the holistic map — skills, contracts, human touchpoints. §4 the command flow (clay → trim → kiln). §5 which skills become wheel workflows (clickable). §6 the per-project testing strategy. §7 the data model · §8–§9 the build + improvement loops · §10 pillars · §11 build sequence · §12 dogfooding · §13 open questions. Every mechanism traces back to a weakness in §1.

1 · The diagnosis — what we have now, criticized

Three parallel audits of the current pipeline (build-prd + the specify→plan→tasks→implement→audit skills, the agents/hooks/coordination, and the self-improvement loop) converged on one punchline:

"The loop is the product" is aspirational, not operational — and build-prd is already mostly autonomous. So the work isn't "add autonomy + self-improvement." It's close a loop that doesn't close, and convert prose-discipline into mechanism.

The findings that carry the redesign

The improvement loop doesn't close 25 open retrospectives, 2 ever closed. kiln-pi-apply last ran ~2 months ago; its logs read "53 stale, 18 parse errors, 5 actionable." Exactly one "apply" commit in project history. Proposals must become self-actionable, not manual diffs.
Precedent is write-only .kiln/mistakes/ holds 2 files total, read by zero build skills. build-prd/specify/plan never read prior mistakes. The precedent-reader is an unbuilt roadmap item. "Context-informed autonomy" has no input. Build the precedent-reader.

2 · The input — vision as the apex

The loop's input isn't "captures." It's captures, filtered and prioritized by the vision, projected through the roadmap, distilled into PRDs. .kiln/vision.md already exists as a holistic outlook — what we're building / what it is not / how we'll know we're winning (signals a–h) / guiding constraints — but today builds don't apply it. It should play three active roles:

role 1 · at intake

Filter

Every idea/feedback/issue is checked against "what it is not" + constraints + "does this match real use?". Accept → roadmap; decline → precedent (the vision names "declined non-goals" as autonomy input).

role 2 · at build time

Context

The build reads vision as top-level context, so act-vs-escalate decisions inherit strategic direction. The constraints are the strategic precedent.

role 3 · continuously

Measure

Signals (a–h) are the system's own acceptance criteria. It scores itself against them; vision-vs-reality drift becomes roadmap items.

The vision already declares the goals the audit found unmet. Signal (c) "capture surfaces close their loops" and (d) "the self-improvement loop closes — and edits land" are exactly what's broken. Much of this rearchitecture is making the system enforce and measure its own vision.md.

The abstraction ladder — the vision is the invariant checked at every rung; a lower rung may never contradict a higher one:

vision.md (holistic · rarely changes)  →  roadmap (phases · typed items)  →  PRD (buildable)  →  spec / plan / tasks (executable)

Open call: should the vision-filter block off-vision work or flag-and-escalate? Leaning flag-and-escalate (decline-with-reason, human can override), since the vision says strategic calls require a human "yes."

Two intake streams — they look alike but go opposite ways

stream A · what to build

Product intent → roadmap → PRD

ideas feedback issues roadmap pass the vision-filter, become roadmap items, distill into PRDs, and build into product code.

stream B · how we build

Operational precedent → ledger → system

mistakes fixes retros go straight to the ledger — fed forward into builds (precedent-reader) and turned into proposals that change skills/agents/templates, never product features. (A mistake exposing a missing capability can be promoted to a roadmap item — explicit escalation, not the default.)

Mistakes are stream B. Conflating them with product captures (as draft v1 did) routes operational failures into the product roadmap — wrong destination.

The design track — Claude-generated HTML, kept in sync

Design is a co-equal input, but the source of truth is repo-resident Claude-generated HTML — layout mockups, a component library, and diagrams — not an external tool. This fits the vision's file-based-state + forkability constraints far better: design is git-diffable, needs no Penpot/MCP, and Claude both generates and reads it. The artifacts live, canonical and forkable, under design/:

  • design/system/ — the design system: HTML component library (the shared SoT).
  • design/features/<slug>/ — per-feature layout mockups, generated from the PRD.
  • design/diagrams/ — system/architecture diagrams as HTML/SVG (this very doc is one).
  • design/manifest.json — maps each design file ↔ the route/component it governs.

How it stays in sync (same "drift = failing test" rule as the canonical docs):

  1. Generate — a design skill (frontend-design / a new /kiln:kiln-design) turns the PRD into mockups composing the design system — the "design" half of plan+design, in the build's design phase.
  2. Gate on UI-change — a PRD that touches UI (flagged ui_change, or detected from UI-path FRs) MUST update design/features/<slug>/ before implement, which then builds to it.
  3. Drift = a finding — audit blocks if a feature touched UI code but its governing design file is stale/missing (and symmetrically, design changed but code not implemented).
  4. Verify by vision — render the mockup + the real app route, screenshot both, Claude-vision-compare → {route, match, diff}. Mismatch is a blocker (replaces trim-verify).
  5. Propagate — when a design/system/ component changes, the manifest fans out to dependent mockups + code as review/regenerate tasks in the improvement queue.

trim + Penpot stay available as an optional adapter for teams already on Penpot — but they're no longer the source of truth.

4 · Command flow — how clay, trim & kiln actually run

Each plugin has its place, and each runs its own inner loop before handing off. Clay runs its real pipeline — clay-idea → clay-idea-research (find/classify similar projects) → clay-project-naming (npm/GitHub/domain checks) → clay-new-product (PRD) → clay-create-repo, tracked by clay-list (idea→researched→named→PRD→repo) — and is *proposed* to also emit vision + user-flows to hand to trim; trim turns those into approvable HTML prototypes; kiln builds from vision + prototype, with an AI smoke-review that drives the real UI and checks it matches the prototype. Two side-channels feed back — report-issue (bugs, fast-fixed) and feedback (features) — and a two-level self-improvement loop closes it (per-repo config vs a separate system-prompt loop). Amber = where you step in. Each stage is clickable → drills into its sub-loop/flow (§5).

6 · Custom testing strategy — per project, not one-size

The audit found smoke-tester + qa-engineer hardcode ports (localhost:5173, 8081) and npm/vite assumptions — so they break on any project that isn't a default Vite web app. A CLI, an API, a library, and a mobile app each verify differently. So testing must be declarative and per-project, read by the audit rather than baked into an agent.

Each project carries a .kiln/test-strategy.json (scaffolded by kiln-init/clay-create-repo from the detected project type, then customized):

{
  "project_type": "web-app",
  "install": "npm ci",
  "build": "npm run build",
  "test": "vitest run",
  "coverage_gate": 80,
  "smoke":   { "start": "npm run dev", "ready": "http://localhost:3000", "probe": "playwright render /", "teardown": "kill" },
  "design_verify": true
}

The audit + smoke-tester read this — "start per smoke.start, wait for smoke.ready, probe per smoke.probe, gate at coverage_gate" — with zero hardcoded assumptions. This also makes the loop framework-agnostic (the vision's language-agnostic direction) and fixes the audit finding by construction. Project-type defaults:

Project typetestsmoke: start → probedesign_verify
CLIunitrun the binary → assert stdout + exit codeno
Server / APIunit + integrationstart server → curl declared endpointsno
Web appunit + e2edev server → Playwright render + vision-verifyyes
Libraryunitinstall into a fresh project → call public APIno
Mobileunitbuild → simulator smokeyes
This is where design-review and testing meet. design_verify: true is what wires vision-verify (render design/ mockup vs the running app) into the audit for UI projects — so a web project can't pass audit on UI drift, while a CLI never pays that cost. One declarative file decides the whole verification shape per project.

7 · Project config — coding standards & review preferences

Two sibling config files sit alongside .kiln/test-strategy.json and are scaffolded by kiln-init / clay-create-repo. Together they answer the two questions every build pipeline needs before it can run autonomously: what quality bar does the code need to meet? and when does a human want to review?

7a · .kiln/standards.md — coding conventions injected at plan + implement

Markdown, not JSON — it feeds directly into LLM prompt prefixes so natural language is more effective than structured data. The framework is explicit-rules (Option 2): rather than referencing a style guide by name and hoping each agent interprets it consistently, the file enumerates concrete directives. Clean Code (Robert C. Martin) is the default template; projects override individual sections without replacing the whole file.

Injected at two points by compose-context.sh: the planner (so contracts and interfaces follow naming rules before any code is written) and the implementer (so function-level rules are enforced at write time). Injecting only at implement is too late — bad names in contracts/interfaces.md propagate everywhere.

## Coding Standards

### Naming
- names are pronounceable and searchable — no abbreviations, no encodings
- one word per concept (fetch not retrieve/get/pull mixed across the codebase)
- functions named as verbs, booleans as predicates (isActive, hasPermission)
- classes and modules named as nouns describing what they ARE, not what they DO

### Functions
- do one thing at one level of abstraction
- <= 20 lines, <= 2 parameters — extract an object or split if more are needed
- no flag arguments — split into two named functions instead
- no side effects — a function that says it reads should only read

### Comments
- do not comment WHAT the code does — rename or restructure instead
- only write a comment to explain WHY: a hidden constraint, a non-obvious invariant,
  a workaround for a specific bug. If removing it wouldn't confuse a future reader,
  don't write it.

### Error handling
- throw exceptions, never return null or error codes from internal functions
- never pass null — guard at system boundaries, trust contracts internally
- fail loudly at boundaries (user input, external APIs), fail silently nowhere

### Structure
- single responsibility — one reason to change per module
- small and cohesive — if you're listing unrelated methods, split it
- tell don't ask — don't reach into an object's state to make decisions for it
- no circular dependencies across layers

### Tests
- one concept per test, assertion names describe the failure
- every test references its spec FR in a comment
- no stubs on integration paths — tests that mock the database teach you nothing

The standards key in .kiln/config.json points to this file so it is swappable — a project with an existing CONTRIBUTING.md can point there instead. Future upgrade: a style key picks a named preset ("clean-code", "google", "airbnb") that gets merged with any local overrides, same pattern as ESLint extends.

8 · The data model — one owner per kind of knowledge

The trap in "multiple sources of truth" is drift: if two places own the same fact, neither does. The resolution is one owner per kind of knowledge — everything else is a mirror or a staging area, never a competing original. The repo owns everything loop-critical and forkable; Obsidian owns the human-facing layer; the task queue makes proposals actionable; the repo's design/ owns the UI design (Claude-generated HTML), kept in sync by a vision-verify gate.

Canonical living documents — the source-of-truth set

Above the granular surfaces (ledger, per-run manifests, per-feature specs) sits a small set of human-facing docs — the narrative a person or a fork reads to understand the project at a glance. Same rule: one owner, one update mechanism, a drift-check. The split that matters is loop-owned (generated, so drift shows in git) vs human-owned (drift becomes an audit finding, like a failing test).

9 · The autonomous build loop

Wheel stays what it is — sequenced routines, not the orchestrator. Autonomy is a thin trigger: a .kiln/ flag flips the existing pipeline from "human drives each step" to "auto-advance," backed by a resumable run-manifest, an escalation sink, and a precedent-reader on the input.

10 · The closed self-improvement loop

This is the part that doesn't exist today. A build emits friction + a retro into the ledger; the ledger generates risk-classified proposals; low-risk ones launch a task that applies them and opens a PR, high-risk ones become one-click chips. The merged change updates the system, and the next build reads the ledger — the loop finally closes.

Mistakes & semantic precedent — the read-forward half

Closing the loop has two halves: writing precedent (covered above) and reading it forward to avoid repeats. The read-forward half is a semantic query over the mistakes + issues ledger, run before a pipeline (and at key steps): retrieve the top-K most-relevant past failures for the current task and inject them as "avoid these known pitfalls." This is "context-informed autonomy" made operational — and it's exactly what the Obsidian copies were always for (queryable issue/mistake data for avoidance), now canonical and forkable in the repo.

11 · The four pillars (+ the thin trigger)

Pillar 1 · fixes "loop doesn't close"

Close the loop

Consolidate .kiln/mistakes + .kiln/fixes + retros into one repo .kiln/ledger/. Build the precedent-reader that injects relevant prior lessons into specify/plan/implement context. Proposals become an actionable task queue (auto-apply low-risk, escalate high-risk).

Pillar 2 · fixes "prose, not mechanism"

Prose → mechanism

A resumable run-manifest (.kiln/runs/<id>/) replacing volatile session state + the stale lock. Structured verdicts (JSON envelopes) for all auditors. Real hooks: coverage gate, untraced-test gate, merge-bar. Reuse watcher-runner.sh for stall detection instead of in-context timers.

Pillar 3 · fixes "no live observability"

Live cockpit

Stream friction-notes + decisions to .kiln/runs/<id>/journal as they happen; render in a watch UI (extend wheel-view from a static inspector into a live run cockpit). The parallel critic writes here too — you see pitfalls as they form.

Pillar 4 · fixes "not forkable"

Forkability

Precedent is repo-resident and machine-read; the GitHub-issue retro store and the personal Obsidian vault drop to optional mirrors. A fork carries its own ledger and self-improves on its own precedent, with or without a vault.

Thin trigger · fixes "autonomy is closer than it looks"

The .kiln auto-run flag

A flag that (a) auto-triggers the distill→build handoff, (b) defines auto-answers for the two stray STOP prompts, (c) routes "ship with known gaps?" through the escalation sink (not a silent auto-yes), and (d) decides merge policy (default: stop at PR; human merges). It only flips safely after pillars 1–2 exist.

12 · Build sequence

All four pillars are in scope, but they have a dependency order — autonomy can't be safe before the mechanisms exist, and self-improvement needs the ledger first.

0
Ledger consolidation + precedent-reader (Pillar 1 core). The highest-leverage single change: make precedent readable and read. Nothing else matters if the loop stays open.
1
Run-manifest + structured verdicts + stall via watcher-runner (Pillar 2 core). Makes a run resumable and machine-judgeable.
2
Live journal + cockpit (Pillar 3). You can now watch before you trust it to run unattended.
3
Actionable proposal queue + auto-apply-low-risk (Pillar 1 completion). The loop closes end-to-end.
4
Real hooks (coverage / untraced-tests / merge-bar) + the .kiln auto-run flag (thin trigger). Autonomy goes live only now.
5
Forkability pass (Pillar 4): demote vault + GitHub-issue stores to mirrors; document the fork story.

13 · How we build this — dogfooding the loop

Self-improving during development is a requirement of the project, not just its output. We build the rearchitecture using the rearchitecture as soon as each piece lands.
  • Ledger first, from day one. The moment Phase 0 ships, every pitfall we hit building the rest goes into .kiln/ledger/ and feeds the next phase's build. The project is its own first consumer.
  • Watch for pitfalls live. Phase 2's cockpit is used to observe Phases 3–5 being built — if the critic/journal can't surface our own mistakes, it isn't done.
  • Forkable from the start. No step may add a hard dependency on the personal vault or yoshisada/ai-repo-template. Every mechanism must work in a clean fork — that's the acceptance test for Pillar 4.
  • Each phase ships behind the flag off. Autonomy stays opt-in until Phase 4; until then a human drives, but the machinery (manifest, journal, verdicts) records everything for the eventual unattended run.
